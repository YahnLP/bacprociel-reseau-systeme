# 🛠️ TP – Monter deux sites, puis les dépanner

*Parcours serveurs – module 1 – individuel puis binôme*

> [!NOTE]
> **Mission.** Sur ta VM `SRV-LINUX`, tu héberges **deux sites** (`site1.local` et `site2.local`) sur un serveur web, tu le sécurises, puis tu **résous des pannes** provoquées par ton binôme.
>
> **Temps prévu :** 3 h (2 séances). **Prérequis :** [cours 1](01-cours.md), [module 0](../m0-virtualbox/02-tp.md), instantané `point-zero`. Garde la [méthode](../methode-depannage.md) et une [fiche de dépannage](../fiche-depannage.md) sous la main.

> **Comment ce TP fonctionne.** Les **commandes sont données** quand on ne peut pas les deviner : ton travail est de les **comprendre** (que fait chaque ligne, pourquoi dans cet ordre, comment je le vérifie). Écris tes réponses aux 🤔 et ❓ **avant** de tester. Le **bilan final** nourrit ton **passeport d'autonomie**.

## Partie B – Deux sites virtuels (≈ 40 min)

1. Crée `/var/www/site1` et `/var/www/site2` avec chacun une page `index.html` **différente** (le nom du site en `<h1>`).
2. Écris `/etc/apache2/sites-available/site1.conf` et `site2.conf` (modèle du cours) avec **un journal par site**.
3. Active-les, désactive le site par défaut, **teste**, recharge :

```bash
sudo a2ensite site1 site2
sudo a2dissite 000-default
sudo apache2ctl configtest
sudo systemctl reload apache2
sudo apache2ctl -S
```

❓ **Je comprends :** que fait `a2ensite` (quel fichier crée-t-il, où ?) ? Pourquoi `configtest` **avant** `reload` ? Pourquoi `reload` plutôt que `restart` en production ? ______________

4. Sur ton PC, ajoute les noms au **fichier `hosts`** puis ouvre `http://site1.local` et `http://site2.local`.
5. Sans toucher à `hosts`, teste : `curl -H "Host: site2.local" http://adresse/`

## Partie F – Dépannage : les pannes de ton binôme (≈ 60 min)

> [!WARNING]
> **Règle :** pendant que ton binôme **diagnostique**, tu **ne dis rien**. Il ne regarde pas ce que tu as modifié. Il suit la **méthode** et remplit une **fiche de dépannage** par panne. Avant de commencer : **instantané** (`avant-pannes`).

Provoque **une** panne à la fois, dans l'ordre que tu veux, **sur la VM de ton binôme à son insu** (ou à tour de rôle sur la même VM) :

| # | Provocation | Symptôme attendu |
|---|---|---|
| 1 | `sudo chmod 600 /var/www/site1/index.html` puis `sudo chown root:root` | 403 sur `site1` |
| 2 | Retire un `>` ou `;` dans un fichier de site puis recharge | le rechargement échoue |
| 3 | `sudo systemctl stop apache2` | *connection refused* |
| 4 | `sudo mv /var/www/site2 /var/www/site2.bak` | 404 sur `site2` |
| 5 | Dans `site2.conf`, remplace `site2.local` par `site3.local` | la page par défaut s'affiche |
| 6 | Lance un autre service sur le port 80 (par exemple `sudo python3 -m http.server 80`) puis redémarre Apache | Apache ne démarre pas |
| 7 | Change le mot de passe dans le PHP | « Access denied » |

Pour **chaque** panne, la fiche doit contenir : symptôme (message exact), hypothèses, **tests réalisés**, message du journal, cause, correctif, vérification, prévention.

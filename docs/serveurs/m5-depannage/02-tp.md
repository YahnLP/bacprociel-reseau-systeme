# 🛠️ TP de synthèse – Le service d'assistance

*Parcours serveurs – module 5 – binôme (un technicien, un « utilisateur-saboteur »)*

> [!NOTE]
> **Mission.** Tu joues le technicien d'un service d'assistance. Ton binôme (qui a lu les « causes cachées » ci-dessous) a **préparé des incidents** sur votre infrastructure. Tu les traites comme dans un vrai service : questions à l'utilisateur, diagnostic, correction, **ticket** et **compte rendu**.
>
> **Temps prévu :** 3 h. **Prérequis :** modules [0](../m0-virtualbox/02-tp.md) et [1](../m1-serveur-web/02-tp.md), idéalement 2 à 4. Outils : [méthode](../methode-depannage.md), [fiche](../fiche-depannage.md).

> [!NOTE]
> **Comment ce TP fonctionne.** Les **commandes et réglages sont donnés** quand on ne peut pas les deviner : ton travail est de les **comprendre** (que fait chaque ligne, pourquoi, comment je le vérifie). Écris tes réponses aux ❓ **avant** de tester. Le **bilan final** nourrit ton **passeport d'autonomie**.

## Préparation

- Infrastructure : une VM serveur avec **un serveur web (deux sites)** + au moins **un autre service** (SFTP ou Samba) selon les modules suivis.
- **Instantané `avant-incidents`.** À restaurer entre deux incidents.

## Règles du jeu

1. L'**utilisateur** ne donne **que le symptôme**, comme dans la vraie vie, et répond **aux questions** posées (sans souffler la cause).
2. Le **technicien** doit **poser des questions utiles**, puis diagnostiquer **avec la méthode**.
3. **Chronomètre** : note le temps passé sur chaque incident.
4. Pour chaque incident : **ticket** (fiche de dépannage) + **compte rendu** de 5 lignes (modèle du cours §4).

## Les incidents

> **Rôle de l'utilisateur-saboteur :** choisis **un incident** à la fois, provoque la cause **sur la VM**, puis joue la plainte. Les causes se trouvent ci-dessous, repliées : **le technicien ne les ouvre qu'une fois l'incident clos**.

| # | Plainte de l'utilisateur | Priorité |
|---|---|---|
| 1 | « Le site de la compta affiche *Forbidden* depuis ce matin. » | |
| 2 | « Le site de la compta affiche la page d'**accueil par défaut** au lieu de notre site. » | |
| 3 | « Je n'arrive plus à me connecter au serveur de fichiers : *mot de passe incorrect*, alors que c'est le bon. » | |
| 4 | « Je peux ouvrir le dossier partagé mais **je ne peux plus y enregistrer**. » | |
| 5 | « Le site ne répond pas du tout ce matin. Rien. » | |
| 6 | « Depuis la mise à jour d'hier soir, mon espace de dépôt se **ferme** quand je me connecte. » | |
| 7 | « Les pages du site se chargent, mais **la partie base de données** affiche *Access denied*. » | |
| 8 | « Plus rien ne marche sur le serveur, même vos outils renvoient des erreurs bizarres… » *(indice : regarde l'espace disque)* | |

<details markdown="1"><summary>🔒 Causes cachées (à n'ouvrir qu'après le diagnostic)</summary>

| # | Cause à provoquer | Diagnostic attendu |
|---|---|---|
| 1 | `sudo chmod 600` sur la page de `site1` (propriétaire `root`) | `curl -I` → 403 ; `error.log` : *permission denied* ; `namei -l` |
| 2 | Remplace le `ServerName` du site par un autre nom | `apache2ctl -S` ; test avec `curl -H "Host: …"` |
| 3 | `sudo smbpasswd -x utilisateur` | `NT_STATUS_LOGON_FAILURE` ; `pdbedit -L` |
| 4 | `read only = yes` ou `chmod 750` sur le dossier partagé | message `ACCESS_DENIED opening remote file` ; `testparm -s` puis `ls -ld` |
| 5 | `sudo systemctl stop apache2` **ou** un autre programme occupe le port 80 | *connection refused* ; `systemctl status` ; `ss -tlnp` |
| 6 | `sudo chown utilisateur:utilisateur /home/utilisateur` (SFTP chrooté) | connexion fermée ; `journalctl -u ssh` : *bad ownership or modes for chroot directory* |
| 7 | Change le mot de passe de `appuser` dans MariaDB ou dans le PHP | `ERREUR 1045` ; `SELECT user,host FROM mysql.user;` |
| 8 | Remplis le disque (`fallocate -l 9G /tmp/gros.bin` sur un petit disque) | `df -h` à 100 % ; `du -sh /var/log /tmp` ; supprimer le fichier |

</details>

## Grille d'évaluation (à remplir par l'« utilisateur » puis l'enseignant)

| Critère | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **Écoute et questions** : le technicien comprend le besoin avant d'agir | aucune question | peu pertinentes | pertinentes | complètes et reformulées |
| **Méthode** : hypothèses classées, une modification à la fois | au hasard | partielle | respectée | respectée et expliquée |
| **Lecture des messages et journaux** | ignorés | partielle | utilisés | utilisés pour **conclure** |
| **Correction** : minimale, sans effet de bord (pas de `chmod 777`) | dangereuse | trop large | correcte | correcte et justifiée |
| **Vérification et communication** | aucune | technique seulement | avec l'utilisateur | + prévention proposée |
| **Documentation** | absente | incomplète | complète | exploitable par un collègue |
